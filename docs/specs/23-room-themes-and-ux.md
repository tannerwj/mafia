# Spec 23 — Room themes and shared UX refinement

**2026-09-26 · Approved direction.** Supersedes Spec 10 only for visual styling and room-wide theme selection. Game rules, role visibility, action ordering, server authority, and the six-role set remain governed by earlier specs. See [design](../superpowers/specs/2026-09-26-room-themes-design.md).

## Goal

Offer Noir Atelier, Midnight Club, and Neon Rain as distinct, room-wide visual themes selected by the non-playing host. Make every player and host screen easier to scan and more inviting, with one obvious next action and clear feedback, while preserving all mechanical and privacy behavior.

## D1 — Protocol and storage

- Add `VisualTheme = "atelier" | "club" | "rain"` in `src/shared/protocol.ts`, `visualTheme: VisualTheme` and nonnegative `visualThemeRevision: number` on **every** `ClientRoomState`, and `set_visual_theme { visualTheme: VisualTheme }` to `ClientMessage`. This is separate from the AI Storyteller's free-text narration theme.
- Store `visualTheme` and `visualThemeRevision` in `RoomMeta` under `ROOM_KEY`; initialize to `atelier`/`0` at claim. A single validated fallback helper maps a missing legacy value to `atelier`/`0`. Include both in every host/player snapshot, even mid-game. `new_game` must preserve them; room wipe removes them with `ROOM_KEY`.
- `set_visual_theme` is authorized only for the host and only in the lobby. Validate the incoming value at runtime against the closed enum. Reject an unknown value with `invalid_visual_theme`, a player with `not_host`, or an in-game request with `not_lobby`. No storage write or broadcast on a rejected or unchanged request. A successful change increments the revision, stores first, then broadcasts to all sockets. It must not modify ruleset, game, scene, or story state. Theme changes count as host room activity, using the existing `touchAndBroadcast` activity policy.
- Theme is a public room property. It must never depend on the viewer's role, seat, faction, pending action, or connection state. Confirm one `snapshot` after reconnect is enough to restore it. If two host tabs set different themes, the last committed `RoomMeta` value wins; the client may apply game-state snapshots in normal order but must not apply a theme value with a lower `visualThemeRevision` than its current room snapshot. Test two-tab convergence.

## D2 — Visual foundation

- Use the same components, DOM order, labels, and actions in all themes. Set `data-visual-theme` on `document.documentElement` from the latest authoritative room snapshot so Radix portals, Sonner toasts, and the global grain layer inherit it; home and pre-welcome render `atelier`. Reset on leaving a room. Derive the selected theme UI from the authoritative snapshot, not local selection state. Use semantic CSS variables for background, surface, text, muted text, border, focus, danger, primary action, and decorative accent. Themes must not use different accent colors or ornament for different secret roles.
- Keep all existing `data-testid` values and asserted state attributes. Existing `--color-*` Tailwind utilities may be remapped, but the names must be semantically stable; no visual theme branches in protocol-sensitive game decisions. Toast/dialog/overlay styles follow theme variables. QR remains on a solid high-contrast light tile.
- No external asset request, CDN, new runtime dependency, WebGL, large bitmap background, or network font. System serif/sans/mono stacks are allowed. Audit existing hard-coded colors in Sonner, grain, phase washes, redaction, and shadows so Club/Rain do not inherit an obvious Atelier cast. Decorative layers are behind controls and `pointer-events:none`. Respect safe-area insets; 44px minimum target; visible focus; readable body text and contrast; no horizontal scroll at 320px. Check body/muted/primary-action text contrast numerically in all three themes.
- Retain the existing interruptible 300ms phase swap. Optional micro-interactions may use CSS or the View Transition API with feature detection, but must never queue a snapshot or keep old secret content visible after a newer projection. All nonessential motion is removed under `prefers-reduced-motion`; theme changes themselves are instant when reduced motion is requested.

## D3 — Shared screen hierarchy

- **Home:** the first viewport states what the game is, offers clear Create and Join actions, and links to an immediately understandable briefing. Preserve existing routes and room creation/join behavior.
- **Host lobby:** show a compact four-step sequence: share room, players join, choose theme/roles, start. Label the new control **Table look** and distinguish the Storyteller's free-text narration theme as **Story setting**. Place a theme picker alongside setup, with stable hooks `theme-picker`, `theme-option-atelier`, `theme-option-club`, `theme-option-rain`, and `theme-status`. Preview means selecting an option commits it through the server and then the authoritative snapshot applies it on all phones; no optimistic local skin. Keep QR/link/code available with an obvious Copy/Share action; keep suggested role counts, validation, Storyteller settings, and all existing house rules. If Start is disabled, show the exact reason next to it. Theme picker indicates the selected value and whether the change was saved; a rejection shows an error. Avoid putting player-join progress below a full-screen QR.
- **Player lobby/seat recovery:** prominently show room code, own seat, joined count, and the next step. Explain role secrecy before starting. No new private data in lobby.
- **Player game:** phase/day and task line first, then valid choices, then the one primary confirm/lock action. Preserve Spec 04's five-second automatic role reveal **only when a role is first assigned**; later reloads/rejoins do not automatically reveal it. Keep role peek and help reachable without theme-coded role visuals. Preserve decoy night controls. An action confirmation should say what was submitted and whether it can be changed. During holding/reveal phases, say what the player should do: wait, listen, acknowledge, or discuss, according to actual phase. Dead view identifies the spectator state without prematurely granting information.
- **Host game:** lead with current phase, readiness/progress, and the next available action. Keep force-advance and absence controls, but make them secondary and explain consequences at the point of use. Keep scene reveal, log, vote board, and narrator controls available. Do not display a role-sensitive denominator or premature tally on player screens. End/rematch screens should make result and next-round path unmistakable.
- Copy must prioritize literal action meaning over theme language. Decorative copy can carry mood but must not tell a role to act when the projected role has no such action.

## D4 — Verification and evidence

- Before implementation, record current compressed JS/CSS sizes and representative home/host lobby/player night screenshots. After implementation, record the same measurements and changes. No new network requests for art/fonts. Explain any significant asset increase.
- Add a Playwright multi-context E2E artifact that uses visible host controls to select each theme and checks player sync, reload/reconnect, rematch persistence, player rejection, and unchanged interaction contract. Do not add unit tests for CSS or simple UI behavior. Use an isolated port and Durable Object state directory for every runner; never delete state while its server runs.
- Run `npm run typecheck`, `npm test`, `npm run test:e2e`, and `npm run build` as the orchestrator. Run a real-click 320/360/390px UI tour of home, host/player lobby, night, day, result, dead, and end for all themes; host at 1024px too. Check keyboard focus, reduced motion, screen-reader labels, safe areas, no overflow, and no decorative tap interception. Record test changes; never remove or loosen failing tests to pass.
- Do not deploy under this spec. The previous live deployment remains untouched until a separate release step is chosen.

Adversarial review must check actual `ClientRoomState` assembly, rematch path, theme-vs-Storyteller naming, stale snapshots, accidental secret/color leaks, and the existing testid set before build.
