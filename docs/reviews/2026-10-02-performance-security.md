## Threat model

The assets are the room's host key, each seat token, hidden role assignments, private night targets and investigative results, hidden ballots, the host-only Storyteller draft/bible, availability of a room, and account-wide Worker/DO/AI quotas. Actors are an anonymous visitor, a visitor who knows a room code, an invited living player, a dead player, the host (possibly in multiple tabs), a malicious host/player, and someone controlling a device or same-origin script. Room-code knowledge permits lookup and a new lobby join; it is **not** host or existing-seat authorization. A UUID host key grants host control; a UUID seat token grants that seat across reconnects and rematches.

Trust boundaries are browser storage → WebSocket `hello` → DO attachment identity; untrusted messages → server/engine; authoritative `GameState` → `projectFor` → serialized frames; public projection plus player names/theme → Workers AI; and error-report bodies → Workers Logs/Analytics Engine. During play, living players should see their own role/knowledge/action, aggregate counts, and only rule-authorized public deaths/votes. Dead players may see roles and resolved history, but not live submissions or hidden ballots. The host has live god view. At game end, role identities become public. The role-count disclosure under hidden death reveals is an explicit product tradeoff in `src/engine/project.ts:103-119` and `docs/PLAN.md`, not a new leak.

## Confirmed security and availability findings

### S1 — High: room and roster resources are unbounded at the app boundary

**Asset/actor/prerequisite:** account-wide Worker/DO quota and a room's availability; anonymous creator or anyone with a valid room code. **Path:** anonymous room creation has no application rate limit, and a known-code guest can repeatedly open pending sockets or join new seats. `handleHello` appends without a player-count check; every join rewrites the roster and broadcasts snapshots to all sockets. `liveSockets` scans all connections repeatedly for presence (`game-room.ts:181-200,620-661,1577-1585,1651-1668`). **Safe observation:** `node scripts/review-local.mjs` joined 21 synthetic players to one fresh isolated room; welcome showed 21 seats despite the ~20-person assumption in `docs/specs/01-protocol-identity-rooms.md:24`. It also measured lobby welcome growth from 1,055 bytes at 3 to 2,663 bytes at 20. This bounded test did not assess a production denial of service. **Expected:** enforce a product-sized seat/socket/pending-auth bound, short pre-auth timeout and edge/app request budgets. **Likelihood/impact/confidence:** moderate likelihood where a code is shared or creation is exposed, potentially high quota/availability impact; high confidence in missing app bounds, unknown live WAF mitigation. **Remediation:** cap seats near the supported UI size, cap pending/authenticated sockets per room and per identity, reject oversize frames before parse, add room-create and error-report rate limits at the edge or Worker. Keep limits compatible with host multi-tab and reconnect storms. **Regression:** bounded E2E that proves the 21st join is rejected while existing seats, duplicate host tabs and reconnects still work; edge rate-rule checks need a separate authorized live configuration review. No DO state migration is required; rollback by removing the guards if a legitimate party exceeds the chosen cap.

### S2 — High: valid repeat submissions grow the entire game log and every broadcast

**Asset/actor/prerequisite:** room availability and hidden history storage; an invited living player with a seat token during a valid phase. **Path:** every same-target `submit_action` appends `actionSubmitted` (`src/engine/machine.ts:155-178`); `applyCommand` clones the complete state with JSON (`machine.ts:9-11,107-109`); the DO rewrites the `game` key and builds a full personalized snapshot for every socket (`game-room.ts:1314-1347,1651-1668`). The log is never pruned in a game. **Safe observation:** ten identical synthetic submissions in a 21-seat local room added ten host-log entries and grew the host snapshot from 6,772 to 8,322 bytes; host-observed input→snapshot p50 5.3 ms, p95 6.5 ms, n=10 on local workerd. The living player's public log still excluded those entries. **Expected:** a repeat of an unchanged tentative action should be idempotent, and retained history should have a defined bound or archival model. [Cloudflare's DO limits](https://developers.cloudflare.com/durable-objects/platform/limits/) put a 2 MB ceiling on a single key/value and allow received WebSocket frames up to 32 MiB, so a long or abusive game can eventually fail storage writes before the platform's socket limit helps. **Likelihood/impact/confidence:** moderate for a player deliberately repeating commands, low for normal play; high room-local impact and high confidence in growth, exact failure threshold not exercised. **Remediation:** skip unchanged submissions, bound per-seat command rate, compact or segment the event history while preserving host/dead resolved history. **Regression:** E2E send the same permitted action twice and assert the second causes neither a new persisted event nor a broadcast; separate long-game integration case should verify history compatibility. Any event-log compaction needs versioned DO state and rollback that can still read old records.

### S3 — Medium: malformed nested WebSocket messages bypass the error path

**Asset/actor/prerequisite:** room handler availability and pending-auth slots; anyone who knows a room code. **Path:** dispatch checks only top-level object and `type`, then `handleHello` accesses `msg.auth.kind` and `.name.trim()` without validating `auth`; other variants dereference `parsed.action.targetId` (`game-room.ts:393-407,424-447,571-627`). `webSocketMessage` has a `finally` metric but no catch that converts these throws into `bad_message` (`game-room.ts:346-367`). **Safe observation:** a local pending socket sent `{"type":"hello"}`. No error frame arrived within one second; the still-open socket's subsequent `ping` got `error:not_authenticated`. This is a missing protocol response, not proof of DO corruption. **Expected:** reject malformed nested data with a bounded `bad_message` response and close or reap predictably. **Likelihood/impact/confidence:** easy to trigger with a room code, low impact per message but amplifies pending-auth and exception/log work; high confidence. **Remediation:** runtime discriminated-schema validation before the switch, including nested types, lengths, finite numbers and enums. **Regression:** local E2E send missing/null/wrong-type `auth` and `action`, assert one error/close and that an authorized socket remains healthy. No state migration; rollback validator changes if compatibility issues appear.

### S4 — Medium: two-hour ended-room cleanup is checked but never scheduled

**Asset/actor/prerequisite:** persistent room state and storage quota; any naturally ended game whose last socket closes. **Path:** alarm handler wipes ended rooms after `ENDED_TTL_MS` (`game-room.ts:1450-1468`), but `scheduleNextAlarm` only queues empty-lobby 1h, absolute 6h and game deadlines (`game-room.ts:1519-1555`). After game end the game deadline is cleared, so an idle ended room normally waits for the 6h alarm. The existing tests backdate the clock and invoke the alarm directly (`test/server/game-room.test.ts:942-1065`); they prove the wipe branch, not that an alarm fires at 2h. This contradicts `docs/specs/17-ops-observability.md:95-98`. **Expected:** enqueue `lastActivityAt + ENDED_TTL_MS` when ended and socket-free. **Likelihood/impact/confidence:** every eligible ended room, storage retention up to about four extra hours, moderate cost/privacy retention impact; high source-path confidence, actual production alarm timing unmeasured. **Remediation:** add ended deadline to the single scheduler and verify transitions/last-socket close. **Regression:** run a real game to ended, close sockets, assert `storage.getAlarm()` is near last activity +2h, then execute the scheduled alarm and assert wipe. No schema migration; rollback scheduler logic if alarms misfire, never delete active-room state.

### S5 — Medium: anonymous error ingestion reads before enforcing its effective size cap

**Asset/actor/prerequisite:** Worker memory, logs and metrics; any anonymous HTTP client. **Path:** the route checks a declared `Content-Length`, but then calls `await request.text()` before its 8 KiB `bodyText.length` check (`src/server/index.ts:123-131`). It accepts arbitrary message, stack, URL, user agent and room-code strings from anyone, logs them and writes a metric with no rate limit (`index.ts:132-157`; `src/server/log.ts:24-33`). A client can omit/lie about length within platform constraints, forcing materialization and creating log noise. **Safe observation:** one synthetic local valid report returned 204 and a 9 KiB report returned 413; no large request or rate test was run. [Cloudflare Workers limits](https://developers.cloudflare.com/workers/platform/limits/) allow request bodies much larger than 8 KiB depending on plan. **Expected:** read a bounded stream, refuse excess bytes early, sanitize/truncate diagnostic fields, and enforce an ingestion budget. **Likelihood/impact/confidence:** public endpoint makes abuse plausible, account-wide impact depends on edge controls and traffic; high source confidence, live WAF unknown. **Remediation:** stream with a hard byte limit or platform-supported body limit, reject overlong fields before logging, apply per-source rate controls. The first-party reporter should strip query strings from URLs and avoid exception messages containing credentials (`src/client/net/errorReporting.ts:124-146`, `ErrorBoundary.tsx:33`). No actual credential-in-log event was observed. **Regression:** chunked local request slightly over cap must 413 without materializing the whole stream; repeated synthetic reports should hit the chosen bound. No DO migration.

### S6 — Low: malformed room-code encoding produces a Worker 500

**Asset/actor/prerequisite:** error noise and request capacity; anonymous caller. **Path:** `decodeURIComponent` is not caught at `src/server/index.ts:113,194`. A bounded local `GET /api/rooms/%ZZ` returned 500. **Expected:** canonical five-character alphabet check and 400/404 before DO lookup. **Likelihood/impact/confidence:** easy but low impact; high confidence. **Regression:** malformed percent and off-alphabet paths return a controlled response and do not create a DO. No state migration.

## Plausible risks and accepted boundaries

- **Storyteller cost/availability (plausible):** host-only generation is limited to 10/min/room and queue-of-one (`game-room.ts:1109-1145,1270-1284`), but its 15-second `Promise.race` does not cancel `env.AI.run()` (`game-room.ts:1207-1219`). A timed-out inference may continue consuming quota/cost; this was not tested against real AI. Model pricing is per tokens for the configured [Llama 4 Scout model](https://developers.cloudflare.com/workers-ai/platform/pricing/); [Workers AI limits](https://developers.cloudflare.com/workers-ai/platform/limits/) are account/model dependent. Bound theme/request ID/bible sizes and normalize runtime types: `set_story_settings` currently persists payload fields without checks (`game-room.ts:1034-1054`), and theme is interpolated into the system prompt (`storyteller.ts:173-191`). Host input can steer story output, but only public facts are passed through `projectFor(..., {kind:"public"})` (`game-room.ts:1140-1154`), and drafts reach host sockets only (`game-room.ts:1165-1177,1286-1301`). No game progress depends on AI output. Prompt injection via a player name/theme could produce misleading narration, not a demonstrated private-role disclosure.
- **Room-code discovery (accepted invitation model):** 31-character alphabet × five positions gives 28,629,151 possible codes (`index.ts:11-12,70-78`); `GET` reveals existence/phase and has no app throttle. A code in an invitation is intentionally usable to join a lobby, never to claim host or an existing seat. Host and seat keys are `crypto.randomUUID()` (`game-room.ts:310,641-647`); no token-guessing success was found. Rate rules at the live edge could change practical enumeration risk, but were inaccessible.
- **Browser and cross-origin boundary:** keys live in per-tab `sessionStorage` with per-room `localStorage` backups (`src/client/net/identity.ts:1-85`), and travel in WebSocket `hello` frames, not URL query parameters. Any same-origin script/XSS can read them; shared-device users can deliberately recover a backed-up seat/host. React text escaping is used, no `dangerouslySetInnerHTML` or player-name HTML interpolation was found. There is no Origin allowlist for WebSocket upgrades, but automatic cookie authentication is absent, so classic cross-site WebSocket hijacking is not established. A remote site still needs a code and may join as a new guest; treat Origin checking as abuse friction, not a substitute for token auth.
- **Headers/cache:** read-only production `GET /` returned HSTS and `X-Content-Type-Options: nosniff`, `cache-control: public, max-age=0, must-revalidate`; no CSP or explicit Referrer-Policy was observed. The cached HTML/static assets contain no personalized state. The host key is returned from a POST API response and seat token only in a personal WebSocket welcome. CSP would add meaningful defense in depth for browser-stored keys, but no confirmed XSS path was found; any policy must accommodate the JSON-LD inline script or move it.
- **Rule variants and disclosure:** explicit public/dead log allowlists at `project.ts:10-65` fail closed for a new event type. `projectFor` gates host live actions, living self-only state, mafia partner state, hidden ballots, and dead resolved history (`project.ts:139-275`). `revealOnDeath` and `votingVisibility` are separately applied. This rechecks the prior P0 `game.log` role-assignment and dead-live-signal leak; the raw-frame E2E passed on this commit. As a product choice, aggregate `rolesRemaining` can reveal a role through count changes after a death even under `revealOnDeath:"none"`.

## Performance baseline and findings

The production build produced 449.45 kB raw / 134.46 kB gzip client JS, 51.43 / 10.45 kB CSS, and 118.76 kB Worker JS. Static production HTML pointed at the same client JS/CSS hashes. The five-load profile used local workerd, Chromium 360×800, 4× CPU throttle, 150 ms latency, 1.6 Mbps down/0.75 Mbps up, cache disabled. These numbers exclude geographically distant network latency and real AI. `STATUS.md` records a **historical single** production AI draft at 2,829 ms and a five-player live game on the deployed application code; those are useful context, not a current sample distribution or proof of today's Worker version.

## Executive summary and priorities

No confirmed host/seat authorization bypass, living-player role leak, dead-player live-signal leak, hidden-ballot leak, or Storyteller private-fact leak was found in the source paths and local checks described above. This is not a claim that the app is secure. The most material confirmed risk is availability/cost amplification from unbounded room creation, seats/sockets and repeat submissions; the two-hour ended-room TTL also does not get scheduled. Real edge controls, server integration tests, production latency and Workers AI behavior remain unverified.

1. **Bound public and known-code resource creation:** cap seats/sockets/frames, hard-limit error ingestion, and verify live edge rate rules. Low-to-medium implementation effort; no DO schema change.
2. **Make accepted commands idempotent and bound history:** prioritize repeat submissions, then define versioned log compaction and snapshot budgets. Medium-to-high effort; protect existing DO state and keep a rollback reader for old records.
3. **Schedule the ended-room 2h alarm and add a scheduling regression:** small fix, but verify no active room is wiped and the 6h backstop still works before deployment. Roll back the scheduler change if alarm behavior differs in live DOs.
