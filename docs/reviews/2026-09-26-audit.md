# In-person game audit — 2026-09-26

Scope of the initial audit: the current React/Worker implementation, its approved specs and house rules, real multi-context Playwright games, 320/360px browser checks, and read-only production probes. Deployment and a production game were separately authorized later the same day; see the release addendum below. The retired README prototype was not used as implementation evidence.

## System and deployment map

`src/client` is a Vite/React/Zustand phone UI. Its `RoomConnection` exchanges authenticated WebSocket commands and authoritative `welcome`/`snapshot` frames. `src/server/index.ts` routes room creation, room pages, and sockets to the SQLite-backed `GameRoom` Durable Object. `src/engine` assigns roles, validates rules, resolves night/day, and projects a separate view for host, player, and public callers. The host is a non-playing arbitrator; players have no chat. Optional Storyteller generation is host-only through Workers AI and is not in the critical game path. Static assets and the Worker are configured for `mafia.tannerwj.com` in `wrangler.jsonc`; local `npm run dev` uses the Cloudflare Vite plugin/workerd. A single DO alarm schedules room lifecycle and game deadlines. Observability is Workers Logs plus Analytics Engine; `docs/RUNBOOK.md` has incident queries.

Documentation drift: `README.md` describes the retired prototype. `docs/PLAN.md` still describes a serif/brass speakeasy direction while the shipped case-file noir UI uses system fonts and olive accents. A later amendment at the top of `docs/specs/02-engine-core.md` correctly specified **locked** Mafia votes on timeout, but two body passages still said “submitted”; this audit corrected those passages without changing the rule. `docs/RUNBOOK.md` covers diagnosis but lacks a deployment/rollback procedure. Keep further edits separate from game-rule changes.

Add fault-injection/live testing only with owner authorization. |

Default rooms are untimed; an idle phone can therefore require the host to mark a player absent or force advance. Those controls worked in full UI drills. This is a host workload/balance tradeoff, not a stranded-game correctness defect. Room storage can expire after six hours of inactivity **with no live sockets**; active sockets prevent that wipe. Existing UI tests cover link/code/QR join, seat claim/reclaim, host reconnect, reload, duplicate tabs, offline return, rapid host double-fire, voting/runoff, death/wins, rematch, and scene holds. They do not simulate an actual sleeping iOS/Android phone or a cross-region mobile network.

## Rerun

From the repository root, with no other Mafia runner using the default 5173 port/state:

```sh
npm run typecheck
npm test
npm run test:e2e
npm run build
```

The main privacy artifact is `test/e2e/projection-privacy.spec.ts`. To run only it on the default runner:

```sh
npx playwright test test/e2e/projection-privacy.spec.ts
```

For parallel runners, assign each a different Vite port **and** `cloudflare({ persistState: { path: "/tmp/unique-mafia-run" } })` in a temporary Vite config, then point a matching temporary Playwright `webServer`/`baseURL` at that port. Stop the server before removing that state. The final audit's isolated run used port 5211 and `/tmp/mafia-final-audit-state-20260926`: 53/53 E2E in 2.3m; typecheck, 200 engine + 54 client + 135 server tests, and build passed.

## Ten-minute table playtest

1. Give a first-time host one phone and 3–5 first-time players separate phones. Say only “start a room and invite everyone.” Observe link/code/QR choice, seating, role editor comprehension, and whether the host can explain why Start is enabled.
2. Play a night with phones physically close. Ask players what they think is private, what Confirm does, and whether anyone can identify a role from **time spent tapping** or a nearby screen. Let one phone sleep; the host must recover the round without coaching.
3. Read the morning announcement aloud, then discuss and vote, including No murder and a changed vote. Ask each player who has voted, what is still hidden, and when the outcome becomes final. Make one player dead and ask whether their case history is interesting without revealing live actions to the table.
4. Finish or force a round, rematch, and ask: “When were you unsure what to do next?”, “Did a reveal feel fair?”, “Did the host have too much work?”, “Would you play this role mix again?” For five players, record how often the game ends after its first kill and whether that was fun or anticlimactic.

## Owner decisions and follow-up

- Pick a small-table pace after a real 3/5/8-player session; approved house roles/rules were preserved here.
- Decide whether default timers should be enabled. Current manual host recovery is reliable in tests but adds work when a phone disappears.
- Authorize any production live-game or deployment check separately. Before one, add a rollback procedure to `docs/RUNBOOK.md` and track DO/Workers AI metrics. This audit made only read-only production requests.
- Test physical phone sleep/backgrounding and slow-cellular transition latency. The multi-context desktop browser suite cannot prove those device-specific behaviors.
